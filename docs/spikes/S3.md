# S3: SSO through the server's desktop-token flow

Issue: #59. Written on 4 November 2026 from the Mattermost server source at
the release tags (`server/channels/api4/user.go`, `server/channels/web/oauth.go`,
`server/channels/web/saml.go`, `server/channels/app/desktop_login.go` and
`webapp/channels/src/components/desktop_auth_token.tsx`) and from Matty's own
implementation (`crates/matty-app/src/deeplink.rs`,
`crates/matty-app/src/main_window/sso.rs`,
`crates/matty-api/src/endpoints/users.rs`).

The end-to-end runs need a Mac, a Docker server with GitLab and Keycloak
(OpenID), and the official Mattermost app installed beside Matty. The cloud
container has none of these, so those rows are **Not run** and list the exact
steps for the reference machine.

## How the flow works on the server

1. Matty opens `{server}/oauth/{service}/login?desktop_token={client_token}`,
   or `{server}/login/sso/saml?desktop_token=…` for SAML. The OAuth and SAML
   handlers keep `desktop_token` in the sign-in state.
2. After the provider signs the person in, the server calls
   `GenerateAndSaveDesktopToken` and redirects the browser to
   `{server}/login/desktop?client_token=…&server_token=…`. It adds
   `isDesktopDev=true` when the client token starts with `dev-`.
3. The webapp's `DesktopAuthToken` page replaces the URL's scheme with
   `mattermost:` (or `mattermost-dev:` when `isDesktopDev` is set) and
   navigates there. If nothing happens, after 10 seconds it shows a message
   under the button.
4. Matty receives `mattermost://{host}/login/desktop?client_token=…&server_token=…`,
   checks the client token against the one it is waiting for, and posts
   `{"token": server_token, "device_id": …}` to
   `POST /api/v4/users/login/desktop_token`. The server checks the token
   against `DesktopTokenTTL` and starts a normal session.

The server never checks the client token at step 4. Only the client checks
it, so the server token works for whichever app receives the link first. This
is what makes the next section matter.

## When the official app is installed

Both apps declare `mattermost://` (Matty in `CFBundleURLTypes` from
`scripts/macos-bundle`; the official app in its own bundle). macOS gives a URL
scheme to one default handler. When more than one app claims a scheme and the
person has never chosen, LaunchServices picks one, and that choice is not
documented. Expect it to be the official app often, because it was usually
installed first. Windows (per-user `HKCU\Software\Classes\mattermost`, where
the last installer to write wins) and Linux (`xdg-mime` default for
`x-scheme-handler/mattermost`) behave the same way: one handler, chosen by
whoever set it last.

If the official app receives Matty's hand-off, it either ignores the link or
signs itself in with the server token. Either way, Matty never sees the
callback and the person is left on the browser page.

### Recommended strategy

1. **Check before opening the browser.** When an SSO sign-in starts, ask the
   OS who handles `mattermost://`:
   - macOS: `NSWorkspace.urlForApplication(toOpen:)`;
   - Windows: `AssocQueryStringW` with `ASSOCSTR_EXECUTABLE`;
   - Linux: `xdg-mime query default x-scheme-handler/mattermost`.

   If the handler is Matty, or nothing handles the scheme, go straight on.
2. **If another app holds it, say so and offer one action.** Show a short
   notice in the SSO waiting view: "Mattermost opens these sign-in links right
   now. Make Matty open them instead?" The action is:
   - macOS 12 and later: `NSWorkspace.setDefaultApplication(at:toOpenURLsWithScheme:)`.
     The system shows its own confirmation, and Matty never changes the
     setting without one;
   - Windows: open `ms-settings:defaultapps`, because Windows 10 and later do
     not let apps set protocol defaults silently;
   - Linux: `xdg-mime default matty.desktop x-scheme-handler/mattermost`.

   The person can also choose "Continue anyway", which is right when they
   plan to quit the official app first.
3. **Never take the scheme back silently** on start-up or after sign-in.
   People who use both apps would find their official app's sign-in broken
   with no idea why.
4. **Fall back to a personal access token** when the hand-off never arrives.
   The waiting view already has a cancel button; add "Use an access token
   instead" after the server's 10-second message would have appeared. That
   path needs no URL scheme at all.
5. **Do not use the mobile flow** with `AppCustomURLSchemes` and `matty://`.
   It needs an admin to change the server, and SAML expects a mobile user
   agent there (PLAN §6.6). It stays a documented option for admins, not the
   default.

Dev builds avoid all of this: their `dev-` tokens come back on
`mattermost-dev://`, which the release builds of both apps never claim.

Steps 1 and 2 are follow-up work. They are filed as #489, a sub-issue of the
SSO epic.

## Minimum server version

| Release | `POST /users/login/desktop_token` | OAuth and SAML honour `desktop_token` |
| --- | --- | --- |
| 9.0.0 | No | No |
| 9.1.0 | Yes | Yes |
| 9.5.0 (ESR) | Yes | Yes |

Checked by fetching `server/channels/api4/user.go` and
`server/channels/web/oauth.go` at each tag. The route is registered at line 66
of `user.go` from 9.1.0 on and is missing at 9.0.0.

Matty's floor stays at **9.5.0**. It is the oldest extended-support release
with the flow, and PLAN §6.3 already supports only the current release and
the last two ESRs, which are newer still. `MINIMUM_VERSION` in
`crates/matty-api/src/capabilities.rs` now says so instead of calling itself
provisional.

One security note for admins: CVE-2024-10214 (fixed in 9.5.10 and 9.11.2) let
accounts that are not SSO accounts use desktop tokens and left an extra
browser session behind. It is a server-side bug and does not change how Matty
signs in, so it does not raise the floor.

## Running it on the Mac

1. Start a Mattermost server with GitLab and Keycloak configured as OAuth and
   OpenID providers. Add SAML only if a license is available; otherwise write
   down that it was skipped.
2. With only Matty installed, sign in with GitLab, then OpenID. Note the time
   from the browser page to Matty's first frame signed in.
3. Run `scripts/dev-bundle` and repeat with the dev build. Confirm that the
   link arrives on `mattermost-dev://`.
4. Install the official Mattermost app, sign in with Matty again, and write
   down which app opens. Then run
   `/usr/bin/python3 -c 'from AppKit import NSWorkspace, NSURL; print(NSWorkspace.sharedWorkspace().URLForApplicationToOpenURL_(NSURL.URLWithString_("mattermost://x")))'`
   to see the handler macOS has chosen.
5. Use the strategy above (once #489 lands) to make Matty the default, sign in
   again, then sign in with the official app and write down what it does.
6. Fill in the "Not run" rows above.
